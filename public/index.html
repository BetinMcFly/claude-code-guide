Claude Code parece intimidante porque casi todo lo que se publica sobre él mezcla lo básico con técnicas avanzadas, sin decir qué va primero. En realidad necesitas cuatro cosas para arrancar. Todo lo demás llega solo cuando el proyecto lo pide.

Puede escribir

lee
archivos, el repositorio, la web
ejecuta
comandos, con el clasificador revisando

Donde arranca la sesión desde agosto de 2026. Claude actúa sin pedirte permiso.

Shift+Tab recorre los cuatro. Tres pulsaciones desde donde arranca la sesión hasta Plan Mode, el único en el que no puede tocar tu código.

01

La jerarquía que nadie te explica

El error más común es querer arquitectar todo desde el principio. Estos tres niveles no son alternativas entre las que elegir: son escalones, y van en orden.

Nivel 1

Lo esencial

Día uno
CLAUDE.md contexto del proyecto /init lo genera por ti Plan Mode Shift+Tab × 3 Auto memory aprende solo
Nivel 2

Productividad

Cuando repitas trabajo
Skills workflows reutilizables Hooks automatizaciones MCP servers conexiones externas
Nivel 3

Arquitectura

Proyectos grandes
Subagents agentes delegados Plugins empaqueta tu setup Worktrees aislamiento Agent teams experimental

La pregunta que más se repite: ¿hay que crear los agentes antes de escribir código?

No. Los subagents, skills y specs son optimizaciones que aparecen cuando el proyecto ya existe y detectas fricción. Crearlos antes es arquitectura especulativa.

02

Plan Mode primero, siempre

El modo en el que Claude investiga y te propone un plan con las herramientas de escritura desactivadas. Nada cambia en tu código hasta que tú apruebes.

Desde agosto de 2026 tu sesión ya no arranca pidiéndote permiso. Arranca en modo automático: un segundo modelo, el clasificador, revisa cada acción en tu lugar y deja pasar lo que considera seguro. Se nota enseguida — Claude edita archivos y ejecuta comandos sin pedirte permiso.

Por eso Plan Mode importa ahora más que antes, no menos: es lo que te devuelve el control sobre cuándo se escribe. Con Plan Mode activo, Claude conserva las herramientas de lectura —abre archivos, busca en el código, consulta la web, ejecuta comandos que no modifican nada— y pierde las de escritura. No puede tocar tu código hasta que apruebes el plan.

La diferencia es la que hay entre pedir e impedir. «No modifiques nada» escrito en el prompt es una instrucción más: Claude puede entenderla a su manera, o perderla de vista veinte mensajes después. En Plan Mode no hay nada que obedecer, porque la herramienta de escritura no está ahí.

Activar 
# La sesión arranca en automático. Pulsa tres veces:
Shift + Tab

# 1ª → ⏸ manual mode on      (solo lectura, te pregunta)
# 2ª → ⏵⏵ accept edits on    (edita sin preguntar)
# 3ª → ⏸ plan mode on        (aquí querías llegar)

# Atajo: /plan entra directo desde el prompt.

Los cinco modos

auto
El modo en el que arranca la sesión. Claude actúa sin preguntarte y el clasificador revisa cada acción por detrás. Para tareas largas y para dejar de pelearte con los permisos.
Manual
Claude lee sin pedirte permiso y te pregunta por todo lo demás. Era el comportamiento por defecto hasta agosto. En la configuración se llama default.
acceptEdits
Claude lee, edita archivos y ejecuta comandos de archivos sin preguntar. Para iterar sobre código que vas revisando sobre la marcha.
plan
Claude lee y ejecuta comandos que no modifican nada, pero no puede escribir. Para explorar antes de cambiar.
dontAsk
Claude usa lo que tengas preaprobado y nada más: cualquier acción que exigiría preguntarte se deniega sola, sin interrumpir. Para CI y scripts cerrados.

Cómo sales de Plan Mode

No tienes que cambiar de modo manualmente. Cuando apruebas un plan, Claude sale de Plan Mode automáticamente y empieza a ejecutar. La aprobación es el cambio de modo.

«ajusta esto…»
Le das feedback y regenera el plan. Sigues en Plan Mode. Puedes quitar pasos, reordenarlos o agregar restricciones.
«yes»
Sale de Plan Mode y ejecuta el plan exactamente como lo aprobaste.
Shift + Tab
Salir sin aprobar nada, por ejemplo si la conversación se desvió y prefieres empezar de nuevo.

Cuándo saltártelo: ediciones de un solo archivo o preguntas de solo lectura. Cuándo es obligatorio: cualquier cambio que toque tres o más archivos, cambios de esquema de datos, o código sensible a seguridad.

/goal, la otra mitad del modo automático

El modo automático evita que Claude te pregunte mientras trabaja. /goal evita que se detenga al terminar. Normalmente Claude acaba su turno y espera tu siguiente mensaje; con un objetivo fijado, un evaluador comprueba al final de cada turno si ya se cumple, y si no se cumple Claude arranca otro turno por su cuenta. Se detiene cuando lo consigue, cuando el evaluador lo da por imposible, o cuando tú escribes /goal clear.

Una condición que funciona 
/goal todos los tests de test/auth pasan y el lint
está limpio, o detente tras 20 turnos

El evaluador solo ve la conversación. No ejecuta comandos ni abre archivos por su cuenta: juzga a partir de lo que Claude ya haya mostrado. «Los tests pasan» sirve porque Claude los ejecuta y el resultado queda en la transcripción. «El código está bien» no sirve.

Añade siempre una cláusula de parada, como «o detente tras 20 turnos». Sin ella, un objetivo que nunca llega a cumplirse deja a Claude dando vueltas turno tras turno.

04

El archivo que ancla todo

Claude Code lee el CLAUDE.md al inicio de cada sesión. Sobrevive a /clear y se recarga desde disco. Es uno de los dos mecanismos que sobreviven de una sesión a la siguiente: este lo escribes tú, el auto memory lo escribe Claude solo.

En Claude Code el contexto pesa más que el prompt. Un buen CLAUDE.md con Plan Mode activo produce mejores resultados que el prompt más ingenioso sin contexto.

Las secciones que importan

Qué es esto
Dos o tres líneas. Qué problema resuelve el proyecto y para quién.
Stack técnico
Lenguaje, framework, librerías, base de datos, deploy, tests, linter. Con versiones cuando importen.
Estructura
Árbol de directorios con un comentario por módulo. Esto le dice a Claude dónde va cada cosa.
Convenciones
Type hints, idioma de los nombres, manejo de errores, dónde van los tests. Lo que un dev nuevo necesitaría saber.
Comandos
Cómo arrancar el proyecto, ejecutar los tests y pasar el linter. Claude los ejecuta directamente.
Decisiones de diseño
Numeradas, con el porqué. Evita que Claude proponga algo que ya descartaste.
Gotchas
Rate limits, secretos, trampas conocidas. La sección que más valor entrega con el tiempo.
Fases
Checklist de qué está hecho y qué falta. Le da a Claude sentido de progreso.
Esqueleto mínimo 
# Nombre del proyecto

## Qué es este proyecto
Una o dos líneas: qué resuelve y para quién.

## Stack técnico
- Lenguaje, framework, DB, deploy, tests, linter

## Estructura del proyecto
src/
├── modulo_a/    # responsabilidad
└── modulo_b/    # responsabilidad

## Convenciones de código
- Reglas concretas, no principios abstractos

## Comandos
- Correr: `comando`
- Tests: `comando`

## Decisiones de diseño
1. Decidimos X en lugar de Y porque Z

## Gotchas
- Trampas conocidas, rate limits, secretos

## Fases
- [ ] Pendiente
- [x] Hecho

Regla de oro para las convenciones: escribe reglas verificables, no principios. «Type hints en todas las funciones públicas» sirve. «Código limpio» no sirve.

Cuando el archivo crece

Apunta a menos de 200 líneas. El CLAUDE.md se carga entero en cada sesión, así que cada línea se paga en contexto siempre — y los archivos largos no solo cuestan más, sino que se siguen peor.

Si se te desborda, no lo recortes a ciegas: mueve instrucciones a .claude/rules/. Son archivos markdown temáticos, y con frontmatter paths: se cargan solo cuando Claude toca archivos que casan con el patrón.

Una regla que solo aplica al backend 
# .claude/rules/api.md
---
paths:
  - "src/api/**/*.ts"
---

Valida siempre la entrada en los endpoints.
Usa el formato de error estándar del proyecto.

Esa regla no ocupa contexto mientras trabajas en el frontend. Una regla sin paths se carga siempre, igual que el CLAUDE.md. Si ya lo tienes grande, /doctor propone recortes: quita lo que Claude puede deducir del propio código y conserva las trampas y el porqué de las decisiones.

05

Prompts que funcionan

De qué partes se compone uno, y los copiables de cada escenario. Todos asumen Plan Mode activo y CLAUDE.md en la raíz.

De qué se compone un prompt

En Claude Code el contexto pesa más que el prompt, así que el prompt no tiene que contarlo todo: tiene que decir lo que el contexto no puede decir por su cuenta. Son cinco partes, y se notan sobre todo cuando faltan.

El resultado
Qué tiene que ser verdad cuando termine, no cómo llegar hasta ahí. Si le dictas el procedimiento a Claude, pierdes lo que mejor hace, que es leer el código y encontrar el camino — y si tu procedimiento era malo, lo ejecuta igual de bien.
El punto de partida
Dónde está lo que tiene que mirar, o la orden explícita de que lo busque él. Si no se lo dices, Claude elige por dónde empezar y acierta a medias.
Los límites
Qué no debe tocar. En un proyecto que ya existe es la parte que más daño evita: el esquema de la base de datos, la API pública, las dependencias.
El criterio de terminado
Algo que se pueda comprobar. «Los tests de auth pasan» sirve; «que quede bien» no. Es la misma regla que sigue el evaluador de /goal en la sección 02.
Qué quieres de vuelta
Un plan, el código, o un plan.md que sobreviva a varias sesiones. Plan Mode ya te garantiza un plan; decir cuál quieres cambia el detalle con que Claude te lo entrega.

Un prompt concreto no es solo más claro: es más barato. Un encargo vago —«mejora este código»— obliga a Claude a rastrear medio repositorio para averiguar a qué te refieres, y cada archivo que abre se paga. Uno que nombra el archivo y el criterio de terminado se resuelve leyendo lo justo.

Y Plan Mode te ahorra la factura más cara de todas: la de implementar en la dirección equivocada y tener que deshacerlo. Lo que cuesta cada hábito está en la sección 06.

En un proyecto nuevo el prompt lo carga todo. No hay CLAUDE.md, ni código, ni convenciones: lo único que Claude sabe es lo que tú escribas. Por eso el primer prompt de un proyecto nuevo no pide código — pide una entrevista.

En uno que ya existe pasa lo contrario: el CLAUDE.md y el propio código ya responden al punto de partida y a los límites, así que el prompt se acorta y se vuelve más concreto. Si en un proyecto existente te sale un prompt larguísimo, no es que lo estés escribiendo mal: es que lo que repites cada vez le falta al CLAUDE.md.

Proyecto nuevo

1 · La entrevista, antes de una sola línea 
Quiero construir [qué hace y para quién, en dos frases].

Antes de escribir código, entrevístame: pregúntame por los
requisitos, el stack, los casos borde y las decisiones de
diseño que debería estar considerando y no he mencionado.

Hazme las preguntas de una en una y espera mi respuesta.

Cuando terminemos, vuelca las decisiones en un CLAUDE.md.
No implementes nada todavía.
2 · Scaffolding 
Crea la estructura del proyecto que acordamos en el CLAUDE.md:
los directorios, un archivo por módulo con un comentario de
cabecera que describa su responsabilidad, el archivo de
dependencias, el .gitignore y un .env.example.

No implementes lógica todavía.
3 · Implementar un módulo 
Implementa [ruta/al/archivo] según el CLAUDE.md.
Incluye los modelos que necesite en [ruta/schemas].
Agrega tests en tests/ siguiendo las convenciones del proyecto.

Un proyecto que ya existe

1 · Entender el repo antes de tocarlo 
¿Qué hace este proyecto? Describe la estructura, lenguaje,
framework, entry points y cómo correr los tests.
No modifiques nada.
2 · Añadir una funcionalidad 
Añade [qué va a poder hacer el usuario cuando esté listo].

El código relevante está en [módulo o ruta]. Si hace falta
tocar algo fuera de ahí, dímelo en el plan antes de hacerlo.

No cambies el esquema de la base de datos, la API pública
ni las dependencias sin avisarme.

Terminado = [los tests de X pasan y puedo hacer Y].

Dame el plan primero.
3 · Corregir un error 
Hay un bug. Esto es lo que observo:

  Error literal:   [pégalo entero, con la traza]
  Para provocarlo: [1, 2, 3]
  Esperaba:        [...]
  Pasa:            [...]

No te doy mi teoría a propósito. Investiga y dime la causa
raíz antes de arreglar nada.

Cuando estemos de acuerdo en la causa, escribe primero un
test que falle por este bug y luego arréglalo.

Ese prompt renuncia a dos cosas a propósito: a darle a Claude tu hipótesis, que sesgaría la búsqueda hacia donde tú ya miraste, y a pedir el arreglo antes que el diagnóstico. El porqué de ambas está en el Flujo A de la sección 03.

4 · Feature grande, con el plan escrito primero 
Escribe un plan.md con los pasos para implementar [feature].
Divídelo en secciones que se puedan ejecutar en sesiones
separadas. No implementes nada todavía.

Qué revisar antes de aprobar un plan

Tres verificaciones que evitan la mayoría de los problemas: que los archivos que va a tocar sean los que esperabas, que las dependencias estén completas, y que respete los gotchas del CLAUDE.md — sobre todo que los secretos no terminen en el repositorio.

06

Cuando Claude empieza a fallar

Repite enfoques que ya descartaste. Olvida restricciones que mencionaste al inicio. Las respuestas se ponen vagas. Eso es saturación de contexto, y se arregla con dos comandos.

Cada archivo leído, cada test corrido y cada intento fallido consume espacio. Conforme se llena, la atención del modelo se reparte entre más contenido y la información temprana pierde peso. No es que el modelo empeore — es que el contexto se ensució.

/compact

Resume y continúa la misma sesión
  • Quieres continuar lo que estabas haciendo
  • Después de un debug largo que sí funcionó
  • Entre pasos del mismo feature
  • Claude se pone lento o vago pero va bien encaminado

/clear

Borra todo, sesión nueva
  • Cambias a una tarea sin relación con la anterior
  • Claude repite el mismo error dos o más veces
  • El contexto quedó contaminado con suposiciones falsas
  • Terminaste un feature y vas al siguiente

Compacta antes de que sea urgente. La compactación automática se dispara cuando el contexto ya casi está lleno — pero en ese punto el modelo ya opera degradado y el resumen sale peor. Compactar manualmente, con espacio todavía disponible, produce mejores resúmenes.

Variantes útiles 
# Ver qué está llenando tu contexto antes de decidir
/context

# Resumir conservando solo lo que importa
/compact enfócate en el bug de autenticación

# Sesión nueva con nombre para encontrarla después
/clear nombre-del-feature

# Recuperar una sesión anterior
/resume

Un detalle que cambia el ritmo de trabajo: el CLAUDE.md se recarga desde disco en cada sesión nueva. Usar /clear entre features no te cuesta las decisiones del proyecto — solo la conversación.

Lo que cuesta cada hábito

El contexto no es solo una cuestión de calidad: es lo que pagas. Claude Code envía la conversación entera en cada petición, así que una pregunta de una línea en una sesión que lleva abierta todo el día arrastra el día entero. De ahí salen casi todas las sorpresas en la factura.

Compactar no es gratis
/compact tiene que leer la conversación que resume, así que compactar un contexto enorme es en sí mismo una petición enorme. Es otra razón para hacerlo pronto. Cuando no necesitas continuidad, /clear no cuesta nada.
La caché caduca
Lo que ya se procesó se relee a precio de caché, pero esa caché dura una hora con suscripción y cinco minutos con clave de API o créditos de uso. Volver a una sesión larga después de comer reprocesa todo el contexto a precio completo.
El razonamiento se paga como salida
El pensamiento extendido viene activado y su presupuesto puede ser de decenas de miles de tokens. Para tareas mecánicas, /effort low lo baja. En los modelos actuales se puede reducir, no apagar.
El modelo, según la tarea
Sonnet resuelve bien la mayor parte del trabajo de código y cuesta menos que Opus. Guarda Opus para decisiones de arquitectura. En un subagente que solo recopila, model: haiku.
Herramientas antes que servidores
Un CLI que ya tienes —gh, aws, gcloud— no añade nada al contexto solo por estar instalado. Un servidor MCP carga los nombres de sus herramientas en todas las sesiones, como dice la sección 09.

Antes de adivinar, mira. /context dibuja qué está ocupando la ventana y señala lo que se puede recortar. /usage da el gasto de la sesión y, con plan de suscripción, marca los comportamientos que se llevan más del 10% — contexto largo o fallos de caché. Y /insights analiza tus últimas sesiones y escribe un informe con dónde se te va el tiempo.

07

Skills: workflows que no vuelves a explicar

Una skill es una carpeta con un archivo SKILL.md dentro. Eso es toda la mecánica.

Claude lee la descripción de cada skill al inicio de la sesión y activa la que coincida con tu petición. El resto del archivo solo se carga cuando se dispara — por eso puedes tener muchos sin saturar el contexto.

Dónde va 
.claude/skills/mi-skill/SKILL.md    # solo este proyecto
~/.claude/skills/mi-skill/SKILL.md  # todos tus proyectos
Anatomía completa 
---
name: revisar-seguridad
description: >
  Úsalo cuando el usuario quiera revisar código por
  vulnerabilidades. Dispara con: "revisa la seguridad",
  "busca vulnerabilidades", "audita este endpoint",
  "esto es seguro?", "checa por inyección SQL".
argument-hint: <ruta o módulo a revisar>
---

# Revisión de seguridad

## Paso 1 — Alcance
- Lee los archivos indicados
- Identifica entradas de usuario y accesos a datos

## Paso 2 — Revisar
Contra esta lista, en orden:
- Inyección (SQL, comandos, plantillas)
- Autenticación y autorización rota
- Secretos en el código o en logs
- Validación de entrada faltante
- Dependencias con CVEs conocidos

## Paso 3 — Reportar
Por cada hallazgo: severidad, ubicación exacta,
por qué es explotable, y el fix concreto.

## Reglas
- NO arreglar nada sin aprobación
- Ordenar hallazgos por severidad, no por archivo
- Si no hay hallazgos, decirlo — no inventar

El campo description es el 80% del trabajo. Es lo único que Claude lee para decidir si la activa. Escribe ahí las frases exactas que dirías en voz alta, no una descripción formal. Si no coincide con cómo hablas, la skill nunca se dispara.

Skill, comando o subagente

Skill
Un workflow que quieres que Claude siga igual cada vez. Claude la activa sola cuando la descripción encaja, y tú con /nombre — ambas cosas van de fábrica, sin configurar nada.
Hook
Un script que corre automáticamente antes o después de una acción. No es conversacional — es plomería.
Subagente
Un asistente con su propio contexto y herramientas limitadas. Úsalo cuando la tarea generaría mucho ruido en tu sesión principal. Es el tema de la sección 08.

Quién puede disparar la skill. Por defecto la disparan los dos: Claude cuando la descripción encaja, y tú con /nombre. Dos campos cambian eso.

disable-model-invocation: true impide que Claude la dispare sola — imprescindible en skills con efectos secundarios, como un deploy, donde quieres ser tú quien decide. Y user-invocable: false la oculta del menú /, útil cuando es conocimiento de fondo y no una acción que tenga sentido invocar.

Una skill debe tener un solo trabajo bien definido. «Revisar seguridad» es una buena skill. «Ayudar con calidad de código» es demasiado amplio y nunca se activa de forma confiable.

Las que ya vienen incluidas

Antes de escribir la tuya, revisa lo que Claude Code trae de fábrica. /code-review revisa el diff, un PR o una ruta, con niveles de esfuerzo de low a max y --fix para aplicar los hallazgos. /simplify limpia y refactoriza sin cazar bugs. /security-review busca vulnerabilidades en el diff. /doctor diagnostica tu configuración. Y /batch parte un cambio masivo en unidades independientes y lanza un subagente por cada una en worktrees aislados.

Con el tiempo acumularás skills que ya no usas, y cada una paga su descripción en contexto en cada sesión. /skill-doctor te dice cuánto cuesta cada una y con qué frecuencia se dispara, para apagar las que sobran.

08

Subagentes: delegar sin ensuciar tu sesión

Un ayudante con su propia ventana de contexto, su propio prompt y sus propias herramientas. Lo valioso no es que sea «otro Claude», es el aislamiento.

Cuando una tarea va a producir mucha salida que no vas a releer —rastrear algo en veinte archivos, revisar un módulo entero, probar tres enfoques— esa salida se queda en tu conversación y te come el contexto. Un subagente hace ese trabajo aparte y te devuelve solo el resumen.

Sirve además para dos cosas menos obvias: limitar qué herramientas puede usar, y mandar el trabajo bruto a un modelo más barato.

Dónde viven y qué forma tienen

Mismo patrón que las skills de la sección anterior: un archivo por agente, en el proyecto o en tu carpeta personal.

.claude/agents/revisor.md 
---
name: revisor
description: Revisa código buscando bugs y problemas
  de seguridad. Úsalo tras un cambio grande.
tools: Read, Grep, Glob
model: sonnet
---

Eres un revisor de código senior. Analiza lo que te
indiquen y reporta cada hallazgo con su ubicación
exacta, por qué es un problema y el arreglo concreto.

No arregles nada: solo reporta.

Solo name y description son obligatorios. Como con las skills, la description es lo que Claude lee para decidir si delega. Van en .claude/agents/ para el proyecto o en ~/.claude/agents/ para todos los tuyos.

No hace falta que lo escribas a mano. Pídeselo a Claude en lenguaje natural — «créame un subagente de solo lectura que revise seguridad y use Sonnet» — y genera el archivo con su frontmatter.

Lo que hereda y lo que no

Esto es lo que más sorprende, y lo que explica casi todos los malos resultados con subagentes.

Sí hereda
Tu CLAUDE.md, el estado de git, y las skills que le indiques precargar.
No hereda
El historial de la conversación, las herramientas que hayas usado, ni el auto memory.

Dicho de otro modo: no sabe de qué habéis estado hablando. Si le encargas «arregla eso que comentamos», no tiene ni idea de qué es «eso». Hay que darle el encargo completo a la primera.

Corren en segundo plano por defecto, así que Claude sigue trabajando mientras tanto, y si el subagente necesita un permiso te lo pregunta en tu sesión principal.

La excepción: /subtask

/subtask no crea un subagente normal, crea un fork: una copia que sí hereda la conversación entera. Es lo que quieres cuando explicar el contexto costaría más que la propia tarea.

/subtask escribe los tests de los cambios del parser

Cuándo NO delegar. Si la tarea necesita ida y vuelta contigo, si varias fases comparten contexto, si es un cambio pequeño y dirigido, o si tienes prisa. Un subagente arranca de cero y eso cuesta tiempo. Delegar un grep es más lento que hacerlo.

Para trabajo genuinamente paralelo que además necesita hablarse entre sí existen los agent teams, varias sesiones coordinándose. Siguen siendo experimentales y vienen desactivados: no los necesitas para empezar.

09

MCP: darle herramientas que no trae

Claude Code trae lo suyo para leer, escribir, buscar y ejecutar. MCP es cómo le das acceso a todo lo demás: tus incidencias, tu base de datos, un navegador.

Un servidor MCP expone herramientas que Claude puede usar como si fueran propias. Los hay alojados, a los que te conectas por una URL, y locales, que Claude Code arranca como un proceso en tu máquina.

Añadir, comprobar, usar 
# Alojado: la documentación de Claude Code,
# que no pide autenticación. Buen primero.
claude mcp add --transport http docs https://code.claude.com/docs/mcp

# Local: un navegador que Claude puede manejar
claude mcp add playwright -- npx -y @playwright/mcp@latest

# ¿Conectó?
claude mcp list

Los comandos van en tu terminal, no dentro de una sesión: configuras el servidor antes de abrir la conversación. Luego no hace falta nombrarlo — Claude elige la herramienta cuando viene al caso.

En claude mcp list los estados que importan son tres: conectado, needs authentication si falta iniciar sesión, y failed to connect si no respondió. Dentro de una sesión, /mcp hace lo mismo y además permite reconectar y autenticar.

Los tres ámbitos

Es lo que más se confunde. Un servidor se registra en un ámbito y ahí se queda.

local
El predeterminado. Solo tú, y solo en este proyecto. Si abres Claude Code en otra carpeta, no está.
project
Se escribe en .mcp.json en la raíz y entra en el repositorio: quien lo clone lo tiene. --scope project.
user
Solo tú, pero en todos tus proyectos. --scope user.

Los servicios como Sentry, Linear o Notion piden iniciar sesión: los añades por su URL y luego /mcp → Authenticate abre el navegador. Los que usan un token lo reciben al añadirlos, con --header.

Cada servidor conectado te cuesta contexto en todas las sesiones, porque sus nombres de herramienta se cargan siempre, lo uses o no. Quita los que ya no utilices con claude mcp remove. Es la misma economía de contexto de la sección 06.

Y un servidor de ámbito project te pide aprobación la primera vez. No es burocracia: evita que un repositorio que acabas de clonar lance procesos en tu máquina sin que lo autorices.

Cuándo agregar cada pieza

No por calendario. Por síntoma.

HerramientaLa señal que te dice que ya toca
SkillEscribiste el mismo prompt por tercera vez. Guárdalo como workflow en lugar de re-explicarlo.
HookQuieres que algo pase automáticamente después de cada edición — lint, format, tests.
Subagente
ver 08		Una tarea recurrente necesita reglas propias y contexto aislado, o genera tanto ruido que ensucia tu sesión.

práctica		Un feature toca tres o más archivos. Escribe el documento de diseño antes de implementar. No es una función de Claude Code, es una forma de trabajar.

El principio que conecta todo: la fase de optimización no es un requisito previo de nada. Es la consecuencia de haber trabajado lo suficiente en las fases anteriores como para saber qué te está costando tiempo.

12

Problemas comunes

Lo que más desconcierta cuando llevas poco tiempo, y la solución que documenta Anthropic para cada caso.

Edita sin preguntar
La sesión arranca en modo automático y el clasificador aprueba por ti. No está roto: es el comportamiento desde agosto de 2026. Shift+Tab una vez te lleva a Manual, donde vuelve a preguntarte. Ver sección 02.
Ignora mi CLAUDE.md
Primero comprueba que cargó: /context lo lista bajo «Memory files». Si está y aun así no lo sigue, suele ser que la instrucción es vaga o choca con otra. Y si algo tiene que cumplirse siempre, no es una instrucción: es un hook.
Compacta en bucle
Si ves que la autocompactación se repite, hay un archivo o una salida enorme rellenando el contexto en cuanto se vacía. Pídele leer el archivo por trozos, usa /compact con un foco que descarte esa salida, o mueve ese trabajo a un subagente con su propio contexto.
Va lento o se traba
/compact libera contexto y memoria. Si sigue pesado, reinicia y recupera con claude --continue: reiniciar no pierde la conversación. Ctrl+C cancela la operación en curso.
Una skill no se dispara
La description es lo único que Claude lee para decidir. Si no coincide con cómo pides las cosas en voz alta, no se activa. /skill-doctor muestra cuáles no se usan nunca.
Algo falla y no sé qué
/doctor revisa instalación, configuración, extensiones y uso de contexto, y propone arreglos que aplica si aceptas. Si Claude Code ni siquiera arranca, claude doctor desde la terminal.

Antes de dar algo por roto: casi todo lo de arriba se diagnostica con dos comandos. /context te dice qué hay cargado y qué lo está llenando; /doctor revisa el resto.
